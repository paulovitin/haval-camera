# Haval Camera video and command protocol

This document is the canonical version 1 contract for later Java, Node, and Swift implementations. All integer fields are unsigned and big-endian unless stated otherwise. Examples are synthetic and contain no captured footage.

## Android command contract

Cross-application commands use explicit actions under `br.com.redesurftank.havalcamera.action.*` and require the signature permission `br.com.redesurftank.havalcamera.permission.CONTROL`. Camera defines and requests this permission so its result broadcast can reach EcoTrip's permission-protected receiver; EcoTrip also requests it to call Camera. Both APKs must carry the approved production certificate. Every journaled command carries protocol version `1`, a non-empty request ID of at most 128 characters, and a non-negative monotonic state revision generated by EcoTrip.

The actions are `START_TRIP`, `STOP_TRIP`, `DISCARD_TRIP`, `RECONCILE`, `START_LIVE`, `STOP_LIVE`, `TRANSFER`, `CANCEL_TRANSFER`, `DELETE_COMPLETED`, `TELEMETRY_SAMPLE`, `GET_SETTINGS`, and `UPDATE_SETTINGS`. `START_MANUAL_RECORDING` and `STOP_MANUAL_RECORDING` are same-package UI actions and are not exported cross-application contracts.

State revisions and settings revisions are separate counters. `RECONCILE` is authoritative and supersedes incremental state commands at the same or lower state revision. Request IDs and accepted state are persisted before an effect is executed. Replayed request IDs, older revisions, and stop/discard commands naming a non-active trip have no effect. `DELETE_COMPLETED` additionally requires explicit owner confirmation and may never delete active or transferring data.

Every journaled command receives one explicit, signature-protected `COMMAND_RESULT` broadcast addressed to EcoTrip after processing. It repeats `REQUEST_ID` and the submitted `STATE_REVISION`, includes `CAMERA_REVISION`, and reports `APPLIED`, `NO_OP`, `STALE`, `REJECTED`, or `ERROR`. `APPLIED` and `NO_OP` confirm completion; the other statuses and a missing bounded acknowledgement do not authorize EcoTrip to persist commanded trip state. Camera sends no credentials or video payload in this result.

If any event that starts recording—including startup journal recovery, a settings refresh, or a remote start—reaches catalog or pipeline work and that effect fails, Camera resets its service state to retryable while retaining crash-safe journal/catalog metadata. Remote processing returns `ERROR`; a later start with a new request ID and revision must attempt the missing recording effect again before it may return `NO_OP`. Replaying the failed request ID remains `REJECTED`.

An automatic `START_TRIP` may reopen a completed catalog entry only when trip ID, original `startMs`, and source match exactly and no read lease is active. Reopening clears completion metadata but preserves every completed segment; new segments continue at the next ordinal. This supports EcoTrip's bounded stop/resume window without creating a second video trip.

`TELEMETRY_SAMPLE` is ephemeral: it is never entered in the request/revision journal. Its monotonic timestamp must not be in the future and must be no more than 2,000 ms old when consumed. The receiver accepts numeric speed and motor-power values only when their validity bits are set; caller-supplied display text is not accepted.

`GET_SETTINGS` returns the full current snapshot and settings revision. `UPDATE_SETTINGS` carries an expected settings revision and a bounded patch. A mismatch returns the unchanged current snapshot and revision. A successful update validates and persists the complete replacement atomically, increments only the settings revision, and returns the confirmed snapshot.

## Live WebSocket authorization

Live producer and viewer credentials are random, one-time, short-lived, TLS-only bearer tokens bound to one session and exactly one scope:

- `live:produce`: one car producer may send binary `HVC1` messages.
- `live:view`: one viewer may receive those messages but may not send video.

The WebSocket session selected by the authenticated URL/token supplies session identity, so the binary header does not repeat a session ID. Tokens are never accepted in another session, role, or transfer protocol and must not appear in logs. The relay does not persist or parse video payloads.

Canonical application close codes are:

| Code | Meaning |
| ---: | --- |
| 4000 | Session ended normally |
| 4001 | Missing or invalid token |
| 4002 | Token expired or already consumed |
| 4003 | Token scope/session mismatch |
| 4004 | Malformed or unsupported protocol message |
| 4005 | Producer replaced or duplicate producer |
| 4006 | Viewer replaced or duplicate viewer |
| 4007 | Backpressure limit exceeded |
| 4008 | Session not found or no longer active |

## `HVC1` live framing

Each WebSocket binary message contains one 24-byte header followed by exactly one payload. No trailing bytes are allowed.

| Offset | Bytes | Field | Value |
| ---: | ---: | --- | --- |
| 0 | 4 | magic | ASCII `HVC1` (`48 56 43 31`) |
| 4 | 1 | version | `01` |
| 5 | 1 | type | `01` CONFIG, `02` ACCESS_UNIT |
| 6 | 2 | flags | bit 0 is keyframe; all other bits are zero |
| 8 | 4 | sequence | per-connection sequence, modulo 2^32 |
| 12 | 8 | PTS | presentation timestamp in microseconds |
| 20 | 4 | payload length | 1 through 4,194,304 bytes |

CONFIG flags are always zero. Its payload is `u16 spsLength + SPS + u16 ppsLength + PPS`; both NAL units are required and each is 1 through 65,535 bytes. There are no Annex-B start codes.

ACCESS_UNIT contains one or more complete AVC NAL units, each encoded as `u32 nalLength + nalBytes` (AVCC). A zero length, truncated NAL, malformed total length, unknown flag/type, wrong magic/version, or payload over 4 MiB closes the connection with code 4004.

The keyframe flag is set only when the access unit is independently decodable. A producer sends CONFIG before the first ACCESS_UNIT and whenever SPS/PPS changes. Viewer join or a drop burst requests a new encoder sync frame; the producer sends the current CONFIG followed by that keyframe. Consumers reset the decoder on changed CONFIG and never continue displaying a stale frame after timeout or decode failure.

## `HVT1` version 1 transfer framing

This section is the authoritative byte contract for Java, Node, and Swift recording transfers. Each WebSocket binary message contains exactly one 56-byte header followed by the declared payload. A concatenated second frame or any trailing byte is invalid. This framing is independent of HVC1; it does not change live video messages.

The authenticated WebSocket credentials supply transfer session identity; no session ID, trip ID, token, or file path is repeated in the binary header. Credentials must be short-lived, scoped to that transfer and role, and never logged. Ordinals identify segments within the authenticated transfer; membership and completed-file metadata are checked by the transfer consumer, not by this codec.

| Offset | Bytes | Field | Value |
| ---: | ---: | --- | --- |
| 0 | 4 | magic | ASCII `HVT1` (`48 56 54 31`) |
| 4 | 1 | version | `01` |
| 5 | 1 | type | `01` DATA, `02` EOF, `03` ACK, `04` ERROR |
| 6 | 2 | flags | `00 00`; no flags are defined in version 1 |
| 8 | 4 | segment ordinal | u32, 0 through 4,294,967,295 at the codec boundary |
| 12 | 8 | offset | u64, 0 through 18,446,744,073,709,551,615; all 64 bits preserved |
| 20 | 4 | payload length | u32, constrained by message type below |
| 24 | 32 | SHA-256 | raw digest bytes, never hexadecimal text |
| 56 | payload length | payload | DATA bytes or ERROR UTF-8 text; absent for EOF/ACK |

All multibyte values are big-endian. Every offset bit pattern is valid at the numeric codec boundary, including values with the high bit set. Java encoder offset parameters and decoded `Message.offset` carry raw u64 bits in a `long`: `Long.MIN_VALUE` represents 9,223,372,036,854,775,808 (`80 00 00 00 00 00 00 00`), and `-1L` represents maximum u64 (`ff ff ff ff ff ff ff ff`). Signed-negative representations must not be rejected merely for their sign. Use unsigned comparison/formatting in Java, `UInt64` in Swift, and exact `BigInt` in Node, without rounding through a JavaScript `Number`. Local file APIs and catalog membership impose consumer-level checks without narrowing this wire domain.

DATA requires the unsigned mathematical sum `offset + payloadLength <= 18,446,744,073,709,551,615`. Crossing the signed-long boundary is valid; wrapping past maximum u64 is invalid. Check before addition with unsigned `offset > maximumU64 - payloadLength` (Java: `Long.compareUnsigned(offset, -1L - payloadLength) > 0`). For a three-byte payload, offset `ff ff ff ff ff ff ff fc` is valid and ends at maximum u64, while offsets `ff ff ff ff ff ff ff fd` through `ff ff ff ff ff ff ff ff` overflow. The Java `int ordinal` parameters carry raw u32 bits: `-1` encodes `ff ff ff ff`; decoded `Message.ordinal` is the unsigned `long` value 4,294,967,295. A consumer still rejects any ordinal absent from its selected catalog.

| Type | Offset meaning | Payload | SHA-256 |
| --- | --- | --- | --- |
| DATA (`1`) | First byte of this chunk within the segment | 1 through `262144` bytes | SHA-256 of exactly this payload |
| EOF (`2`) | `totalBytes`, the complete segment size | Zero bytes | Whole-segment SHA-256 from completed catalog metadata |
| ACK (`3`) | `nextOffset`, the first unpersisted byte | Zero bytes | All 32 bytes zero |
| ERROR (`4`) | Always zero | 1 through `1024` bytes of strict UTF-8 | SHA-256 of exactly these UTF-8 bytes |

DATA and ERROR digests must match before accepting their payloads. Empty DATA/ERROR messages are invalid. ERROR limits count encoded bytes, not characters; malformed UTF-8, overlong encodings, truncated sequences, and unpaired Java surrogates are rejected rather than replaced. A valid ERROR is an application failure, not malformed framing; its text must not contain credentials, paths, or captured data.

EOF's digest is not a hash of its empty payload. The codec preserves any supplied 32-byte digest; a receiver must compare its durably stored complete segment size and whole-file SHA-256 against EOF and completed catalog metadata before promoting the file. The codec cannot verify a whole file it does not own.

An ACK confirms that every byte before `nextOffset` in that segment is durably persisted and verified. `nextOffset = 0` confirms no bytes. An ACK does not confirm socket receipt alone, authorize skipping bytes, or imply EOF completion. A transfer consumer must validate the ordinal, expected offset, and segment bounds before advancing or resuming; these stateful checks are outside this codec.

### Transfer failure and close behavior

A wrong magic/version/type, any nonzero flag, unsigned DATA end-offset overflow, invalid per-type field/length/digest, truncated header or payload, invalid UTF-8, or trailing byte rejects the entire message. ERROR still requires offset zero. Never persist bytes or advance an ACK after rejection. The Java decoder throws `IllegalArgumentException` and leaves the caller's buffer position, limit, mark, and byte order unchanged on both success and failure. It reads only the remaining bytes, including direct/read-only buffers. Encoders return a buffer at position zero with limit equal to the full frame length; payloads and digests are copied, and decoding returns arrays independent of the input buffer.

The transport consumer must close malformed or unsupported messages with code `4004`. It must not try to send an ERROR in response to malformed/untrusted framing. Existing authentication/session close codes above retain their meanings. A valid ERROR terminates the current transfer attempt without acknowledging further bytes; the consumer ends the session normally with `4000` and preserves the last durably verified offset for any newly authorized retry. A successfully verified EOF completes its named segment; the session ends normally with `4000` once all requested segments are complete. Network loss never implies an ACK; retries require fresh scoped credentials. These are consumer requirements; this codec implements no sockets, sessions, credentials, files, or retries.

## Camera recording transfer producer

`RecordingTransfer` implements HVT1 on a dedicated single worker and a dedicated
WebSocket/OkHttp dispatcher. It shares only session validation and client creation
with `VideoRelayClient`; it never uses the HVC1 frame queue. One reusable
`262144`-byte file-read buffer serves both whole-file verification and chunk
reads. Codec frame allocations and immutable WebSocket payload copies are bounded
by one outstanding DATA/EOF, not retained as a retransmission cache.

The signature-protected `TRANSFER` command retains the journal/version/revision
rules above. It requires `TRIP_ID`, `SEGMENT_IDS` (String ArrayList, 1–256 unique
catalog ordinals), `SESSION_URL`, `PRODUCER_TOKEN`, `EXPIRES_AT_MS`, `SESSION_ID`
and `VIEWER_SESSION` (both exactly the URL session). Additive extras under
`br.com.redesurftank.havalcamera.extra.*` are:

| Extra | Android value | Bridge command field |
| --- | --- | --- |
| `OFFSETS` | Bundle: selected ordinal keys to unsigned decimal strings | `offsets` |
| `COMPLETED_SEGMENT_IDS` | optional String ArrayList, default empty | `completedSegmentIds` |
| `PAUSED` | boolean, default true | `paused` |

Every selected ordinal must have exactly one offset. Completed ordinals must
belong to the selection and have offset equal to segment size. URLs require WSS,
no user info/fragment, exactly the session query, and path
`/ws/video/transfer/car`. The bearer token stays in `Authorization`, never the URL
or logs. `CANCEL_TRANSFER` requires the matching `SESSION_ID` while a producer
exists. Remote downloads disabled rejects transfer and cancels an existing one
when settings refresh. Transfer startup/transport failures acknowledge a safe
command error or end only transfer state; they never dispatch `PIPELINE_FAILED`,
start capture/encoder, or stop an existing recording.

Initial socket connection never authorizes DATA/EOF, including when `PAUSED` is
false. The bridge may attach the producer before the viewer. Camera accepts the
approved bridge controls `{"type":"pause","reason":"viewer"}` or reason `live`,
and `{"type":"resume","offsets":{"1":"0"}}` (all selected ordinals required).
These controls use the canonical field order shown; whitespace is allowed.
Unknown/duplicate members, unexpected offsets and malformed controls close 4004.
A duplicate resume while already running preserves its outstanding frame.

Pause retains the last durable ACK and the catalog lease, sends nothing further,
and accepts a matching in-flight ACK. Only explicit resume clears an unacknowledged
frame that the bridge may have discarded and rereads from the confirmed offset.
Local live has priority. Local live end alone does not resume; an explicit bridge
resume received while local live is closing is remembered and can run after local
live ends. The bridge stores only pending metadata and must never cache sent bytes.

Before connecting, Camera leases the completed trip and validates every selected
catalog segment and its exact file size. Opening payload content additionally
requires that catalog's active lease and refuses symlinks/path aliases. Active
trips, `current.partial`, missing files, traversal and unselected IDs cannot be
transferred. Payload reads use `RandomAccessFile.seek` at the authorized ACK.
Before first DATA or resumed EOF for each segment, the worker verifies the whole
file against completed catalog SHA-256 using the same read buffer. DATA hashes
come from `TransferChunkCodec`; EOF contains completed size and whole-file digest.
Wire u64 values remain exact: decimal input uses `Long.parseUnsignedLong` and
bounds use unsigned comparison. Values above local non-negative file length are
refused at this file boundary without narrowing the codec's u64 domain.

Only a matching ordinal and exact pending end offset can ACK DATA/EOF. EOF needs
its own final ACK even when DATA's last ACK already equals file size. One frame
is outstanding at a time; a busy socket queue delays reads instead of accumulating
another queue. Send completion, pause, timeout and network loss never advance an
ACK. Failure/close/expiry never reconnect automatically. A newly journaled command
must supply fresh scoped credentials and bridge-authorized offsets/completed IDs;
a producer instance also refuses reuse of a consumed token (stores its hash only).

Completion, cancellation, replacement, expiry, invalid ACK/control, ERROR, network
loss and file/connect/send failures all release ownership. If a worker is reading,
termination first disables sends, then retains its lease until the file closes;
only then does it report completion. Service destruction closes the transfer too.
Catalog index publications notify a listener; the service posts a
`ContentResolver.notifyChange` for `content://br.com.redesurftank.havalcamera.video/trips`
so completed-file changes and retention/deletion can trigger metadata refresh.
Lease changes themselves do not publish catalog changes.
